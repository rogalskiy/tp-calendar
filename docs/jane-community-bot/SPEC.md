# Jane Community Support Bot — ТЗ и план реализации

Статус: черновик v0.1 (2026‑09‑06). Ждёт ответов на открытые вопросы в конце.

## 1. Зачем

Комьюнити‑чат Jane в Telegram растёт, поддержка читает его руками. Теряются вопросы без ответа, нет цифр по тематикам, FAQ обновляется по памяти. Бот берёт на себя рутину: следит за чатом, сигналит о зависших вопросах, считает статистику и предлагает обновления базы знаний.

Три задачи в порядке приоритета:

1. **Неотвеченные вопросы** — видеть их и алертить поддержку.
2. **Аналитика** — обращения по тематикам и динамике, включая всю историю чата.
3. **FAQ / база знаний** — находить повторяющиеся вопросы и предлагать готовые записи.

## 2. Принципы

- **Бот не пишет в комьюнити‑чат.** Только читает. Все алерты, отчёты и черновики уходят в отдельную рабочую группу поддержки. Это снимает риск, что бот от лица Jane даст медицинский или регуляторно опасный ответ.
- **Человек утверждает всё, что попадает в FAQ.** Бот готовит черновик, поддержка нажимает «Утвердить» или правит.
- **Ложные алерты дороже пропусков.** Если бот дёргает поддержку из‑за болтовни, его выключат. Точность «это вопрос, нужен ответ» важнее полноты, порог настраивается.
- **Минимум данных.** Храним текст сообщений и метаданные, не храним медиа. Доступ к базе только у команды.

## 3. Ограничения Telegram, которые определяют архитектуру

| Ограничение | Следствие |
|---|---|
| Bot API не отдаёт историю до момента добавления бота в чат | Историю «за всё время» забираем один раз через экспорт Telegram Desktop (JSON) и импортируем |
| Бот видит все сообщения группы только с выключенным privacy mode или с правами админа | Добавляем бота админом без прав модерации |
| Удаления сообщений боту не приходят, реакции приходят только админу с `allowed_updates` | Статусы «решено» ставим по ответам и кнопкам, реакции — как дополнительный сигнал |
| Ссылка на сообщение в супергруппе: `t.me/c/<id без -100>/<msg_id>` (в темах форума `/<topic>/<msg>`) | Алерт содержит прямую ссылку, поддержка отвечает в один клик |

Альтернатива — user‑bot на MTProto (Telethon): читает историю сам, но нужен живой аккаунт и есть риск бана. В v1 не используем, держим как запасной путь, если экспорт неудобен.

## 4. Архитектура

```
Telegram комьюнити‑чат ──(Bot API, long polling)──► Ingest ──► PostgreSQL
Экспорт истории (JSON) ──(разовый импорт)─────────► Ingest ──►    │
                                                                  ▼
                                              Classifier (Claude, структурный JSON)
                                                                  │
                        ┌─────────────────────────────────────────┼──────────────────────┐
                        ▼                                         ▼                      ▼
              Answer tracker + SLA timer              Analytics (агрегаты, /stats)   FAQ miner (еженедельно)
                        │                                         │                      │
                        └──────────────► Рабочая группа поддержки в Telegram ◄───────────┘
                                         (алерты, отчёты, черновики FAQ, кнопки)
                                                                  │
                                                                  ▼
                                                    База знаний (markdown в git или Notion)
```

Один процесс на Python: aiogram 3 (Telegram), PostgreSQL, APScheduler (таймеры и еженедельные задачи), Anthropic SDK. Хостинг — Railway или Fly.io (~$5–10/мес) либо небольшой VPS. Docker‑образ, деплой из GitHub.

Отдельный репозиторий `jane-community-bot`. Этот документ переедет туда.

## 5. Модель данных

- `chats` — id, название, тип, часовой пояс.
- `users` — telegram id, username, имя, `is_staff`, роль (support / team / moderator / member).
- `messages` — chat_id, msg_id, thread_id, user_id, reply_to_msg_id, текст, тип медиа, sent_at, edited_at, источник (live / export), сырой JSON.
- `topics` — таксономия тематик: id, название, описание, родитель, активна ли.
- `requests` — обращение, привязано к сообщению: тип (вопрос / баг / предложение / жалоба / отзыв), topic_id, срочность, краткое резюме, статус (`open`, `answered_by_staff`, `answered_by_community`, `resolved`, `dismissed`), время первого ответа поддержки, время первого любого ответа, кто взял, число алертов, время последнего алерта.
- `alerts` — request_id, когда отправлен, msg_id в рабочей группе, уровень эскалации.
- `faq_entries` — вопрос, ответ, topic_id, статус (`draft`, `approved`, `rejected`, `outdated`), ссылки на исходные обращения, кто утвердил.
- `reports` — период, текст отчёта, агрегаты в JSON.

## 6. Функциональные блоки

### 6.1 Ingest

- Long polling по Bot API, приём `message`, `edited_message`, `message_reaction`.
- Каждое сообщение пишется в `messages` идемпотентно (chat_id + msg_id).
- Импорт экспорта: парсер JSON Telegram Desktop → те же таблицы, источник `export`. Повторный импорт не дублирует.
- Список сотрудников поддержки — в конфиге по telegram id, плюс команда `/staff add @user` в рабочей группе.

### 6.2 Классификация (Claude)

Каждое сообщение не от сотрудника уходит в Claude вместе с контекстом (до 5 предыдущих сообщений в той же ветке или цепочке reply) и списком тематик. Ответ — строгий JSON через structured outputs (`client.messages.parse()` с pydantic‑схемой):

```
is_request: bool           # это обращение, а не болтовня / реакция / ответ другому
kind: question | bug | feature_request | complaint | feedback | other
topic: <id из таксономии> | "unknown"
urgency: low | normal | high   # high: не могу войти, списали деньги, ошибка в результатах
needs_staff_reply: bool    # даже если это вопрос, иногда ответ не нужен
summary: str               # одна строка на русском для алерта и отчёта
```

Модель — `claude-opus-5`, адаптивное мышление, `effort: low` (классификация не требует глубокого рассуждения). Системный промпт с таксономией и примерами закэширован (prompt caching), меняется только сообщение. Языки чата: украинский, русский, английский — промпт это учитывает.

Исторический импорт гоняем через Batch API (в два раза дешевле, без спешки).

### 6.3 Отслеживание ответов и алерты

Обращение считается отвеченным, если:

- сотрудник ответил через reply на сообщение или упомянул автора — правило, без LLM;
- сотрудник написал в той же теме в течение 30 минут без reply — Claude подтверждает «это ответ на обращение X»;
- автор написал «спасибо, помогло» или похожее — статус `resolved`;
- ответил другой участник — статус `answered_by_community`, алерт идёт с пониженным приоритетом (настраивается: можно не алертить вовсе).

SLA и алерты (значения по умолчанию, настраиваются):

| Событие | Когда |
|---|---|
| Первый алерт | 30 мин без ответа в рабочие часы (пн–пт 10:00–19:00 Киев) |
| Повтор | через 2 часа, затем через 24 часа |
| Вне рабочих часов | `urgency: high` — сразу; остальное — дайджест в 10:00 следующего рабочего дня |
| Утренний дайджест | 10:00 ежедневно: все открытые обращения с возрастом |

Формат алерта в рабочей группе:

```
🔴 Без ответа 47 мин · Оплата · high
@ivan: «Оплатил чекап, деньги списались, а статус в приложении не поменялся»
→ открыть сообщение
Похожий FAQ: «Статус оплаты обновляется до 15 минут…»
[Беру]  [Отвечено]  [Не вопрос]
```

Кнопки: «Беру» назначает сотрудника и останавливает повторы на 2 часа, «Отвечено» закрывает, «Не вопрос» закрывает и попадает в набор для дообучения промпта. Строка «Похожий FAQ» — подсказка поддержке из базы знаний, чтобы ответить быстрее.

### 6.4 Аналитика

Команды в рабочей группе:

- `/stats` — за 7 дней по умолчанию, `/stats 30d`, `/stats 2026-06..2026-08`, `/stats all`.
- `/topics` — распределение по тематикам с примерами.
- `/unanswered` — открытые обращения сейчас.
- `/export 30d` — CSV с обращениями.

Метрики: число обращений, доля по типам и тематикам, динамика к прошлому периоду, медианное время первого ответа поддержки, доля ответов в SLA, число неотвеченных, топ‑5 болей с примерами, всплески (тематика выросла ×2 за неделю — отдельно подсвечиваем: обычно это релиз или инцидент).

Еженедельный отчёт: понедельник 10:00, Claude пишет 10–15 строк по агрегатам плюс таблица тематик. История за всё время — тот же механизм по импортированным данным.

Таксономия строится на истории: Claude читает выборку из экспорта, предлагает 15–25 тематик с описаниями, команда правит, дальше все обращения классифицируются по утверждённому списку. Тематики можно добавлять и объединять, переклассификация — по команде.

Дашборд с графиками — не в v1. Если понадобится, подключаем Metabase к той же базе.

### 6.5 FAQ и база знаний

Еженедельная задача (можно запустить командой `/faq-scan`):

1. Берём обращения за последние N недель (по умолчанию 4) плюс всё, что уже накопилось в истории.
2. Claude группирует обращения в кластеры «один и тот же вопрос разными словами» внутри тематики.
3. Кластер из ≥3 обращений сравнивается с текущей базой знаний. Если записи нет — черновик: формулировка вопроса, ответ, синтезированный из реальных ответов поддержки в чате, ссылки на исходные сообщения.
4. Если запись есть, но ответы поддержки в чате ей противоречат — пометка `outdated` с диффом.
5. Черновики уходят в рабочую группу с кнопками «Утвердить» / «Править» / «Отклонить». Утверждённое пишется в базу знаний.

База знаний в v1 — markdown‑файлы в git‑репозитории (бот делает коммит). Если FAQ живёт в Notion или на сайте, добавляем интеграцию записи туда. Вся база небольшая и целиком помещается в контекст, поэтому отдельный поиск и эмбеддинги не нужны: она идёт в закэшированный системный промпт.

Ответы с медицинским содержанием черновик помечает отдельно: их обязательно проверяет тот, кто отвечает за клинические формулировки.

## 7. Качество: как поймём, что работает

До запуска алертов на живую команду:

- Размечаем вручную 150–200 сообщений из истории: «обращение / не обращение», «нужен ответ поддержки», «отвечено / нет».
- Цели: точность «нужен ответ» ≥ 0.9, полнота ≥ 0.85; определение «отвечено» ≥ 0.9.
- Первую неделю алерты идут в тестовую группу, смотрим долю нажатий «Не вопрос». Порог — меньше 10%.
- Кнопка «Не вопрос» копит примеры для правки промпта.

## 8. Данные и безопасность

- В чате могут быть личные данные о здоровье. База — на хостинге в ЕС, доступ по ролям, бэкапы шифрованные.
- Храним текст и метаданные, медиа не скачиваем.
- Сообщения уходят в Anthropic API для классификации. По коммерческим условиям API данные не используются для обучения. Срок хранения и договорные условия проверяем перед запуском.
- Токен бота, ключ API, строка подключения к базе — в секретах хостинга, не в репозитории.
- Срок хранения сырых сообщений — обсудить (например, 24 месяца, дальше только агрегаты).

## 9. Оценка стоимости

Допущения: 200 сообщений в день, история 30 тыс. сообщений. Все цифры — оценка, уточним по первым неделям.

| Статья | Оценка |
|---|---|
| Хостинг + PostgreSQL | $5–10 / мес |
| Claude API, живой поток (классификация + проверка ответов + отчёты), `claude-opus-5` с кэшем | $60–80 / мес |
| Разовый импорт истории через Batch API | $100–150 за 30 тыс. сообщений, линейно от объёма |
| Telegram | бесплатно |

Рычаг, если объём окажется больше: перевести массовую классификацию на `claude-sonnet-5` (в 2,5 раза дешевле). Решение за вами, по умолчанию везде Opus 5.

## 10. План работ

Каждый этап — отдельная сессия / PR, результат проверяем на реальных данных.

**Этап 0. Доступы и решения (полдня, нужны действия с вашей стороны)**
- Ответы на открытые вопросы из раздела 11.
- Токен бота от BotFather, бот добавлен админом в комьюнити‑чат.
- Рабочая группа поддержки, бот добавлен туда.
- Экспорт истории чата из Telegram Desktop (JSON, без медиа).
- Список telegram id сотрудников поддержки.
- Ключ Anthropic API, аккаунт на хостинге.

**Этап 1. Ingest + алерты (2–3 дня)**
- Репозиторий, Docker, деплой, база, миграции.
- Приём сообщений, импорт экспорта.
- Классификатор, детекция ответов, SLA‑таймер, алерты с кнопками.
- Алерты в тестовую группу, первая калибровка порогов.

**Этап 2. Таксономия и аналитика (2 дня)**
- Таксономия по истории, утверждение командой.
- Классификация всей истории через Batch API.
- Команды `/stats`, `/topics`, `/unanswered`, `/export`, еженедельный отчёт.

**Этап 3. FAQ (2–3 дня)**
- Кластеризация, черновики, кнопки утверждения, запись в базу знаний.
- Подсказка «Похожий FAQ» в алертах.

**Этап 4. Калибровка (1 неделя фоном)**
- Разметка выборки, замер точности, правка промптов.
- Перевод алертов из тестовой группы в рабочую.

Итого: MVP с алертами и аналитикой — около двух недель календарно, FAQ — ещё неделя. Дальше бот живёт на автопилоте, правки по обратной связи поддержки.

**Не делаем в v1:** ответы бота в комьюнити, автопубликацию FAQ без утверждения, веб‑дашборд, интеграцию с тикет‑системой (легко добавить позже: кнопка «Создать задачу» → Linear / ClickUp).

## 11. Открытые вопросы

Ответы меняют дизайн, поэтому нужны до этапа 1.

1. **Чат.** Один чат или несколько? Включены ли темы (forum topics)? Сколько примерно сообщений в день и какой объём истории?
2. **Кто поддержка.** Фиксированный список аккаунтов? Считать ли модераторов из комьюнити «ответившими»?
3. **SLA.** Какое время ответа считаем нормой и в какие часы работает поддержка?
4. **База знаний.** Где сейчас живёт FAQ — Notion, сайт, Google Doc, нигде? Куда бот должен писать утверждённые записи?
5. **Экспорт истории.** Кто может сделать экспорт из Telegram Desktop (нужен аккаунт участника чата)?
6. **Хостинг.** Railway / Fly.io за $10 в месяц устраивает или нужна инфраструктура Jane?
7. **Ответы от комьюнити.** Если участник ответил раньше поддержки — снимаем алерт или оставляем на проверку?
